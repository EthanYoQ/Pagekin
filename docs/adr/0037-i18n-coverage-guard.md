# i18n 覆盖守卫的判定口径

2026-11-26，注释清理（#852）第 1 个 PR（scripts）。

## 背景

`scripts/check-i18n-coverage.mjs` 拦截渲染层与主进程边界上「只有中文或只有英文」的文案、数量复数错误、以及把原始错误码或原文交给作者的写法。它的判定口径来自 #408、#471、#474、#725 等一系列缺陷，原先写在源码注释里，现迁到这里。

## 决定

### 一、扫描范围

1. 宽泛的渲染根保留既有的可见文案检查；边界根刻意很小，只对应真实的面向用户的错误交付路径，而不是一份不断增长的字符串字面量允许清单。排除项是语义的，不是逐文件的：扫描器只跟随到达渲染汇（toast、提示框、报错状态、`text()` 拼接）或主进程「返回错误」边界的文案。模型提示、解析诊断与仅写 console 的日志不跨这两条边界，扫描它们只会制造误报，对用户看到的语言没有帮助。
2. 工作流命令里 `throw new Error(...)` 的说明原样进运行卡片的失败说明，不能是只有中文或只有英文的原文，也不能是主进程转来的原文。整串的稳定错误码（如 `GENERATION_DRAFT_RECEIPT_INVALID`）不拦：登记过的由失败面板按界面语言解释，其余按 `generation-error-codes.test.ts` 的约定留给反馈定位。严格命令目录里连错误码也不能直接抛（#408）。
3. 命令目录以外的工作流文件抛出的说明同样进运行卡片、启动报错或恢复对话框（#471、#474），不能写只有中文或只有英文的原文。不拦转出的 `.error`、`.message`：这些文件还转出渲染端已按界面语言写好的说明，语法上分不开；主进程原文的转出由各处改用 `workflowMainProcessError` 处理。
4. 工作流目录以外的渲染层文件（含 `src/shared`）抛出的说明会经各处 `catch` 显示给作者（#474），同样不能只有中文。纯内部断言或只进日志的，在 `throw` 所在行或上一行写 `// i18n-exempt: <理由>`；同一个解析或校验函数里的多处可以写在函数声明正上一行（该指令覆盖整个函数体）。`Promise.reject(new Error(...))` 按 `throw` 算。**理由为空也算违规**：豁免必须说得出为什么作者看不到。
5. 渲染层把报错交给作者的显示处，主进程的 `result.error`、IPC 抛出的错误与 `catch` 到的原因不能原样交给 toast、提示框、报错状态或拼进 `text()`，要先经 `displayedErrorMessage`（或同类翻译函数），否则主进程的错误码会以裸码出现在界面上。

### 二、英文数量与复数

1. 数量后的英文复数名词，中间可隔一两个修饰词（`the ${n} existing blueprints`）：数量是 1 时读成「1 chapters」，要走 `pluralEn`；插值后接 `checks`、`changes` 作动词也会被拦，改写句子或用 `pluralEn`。`these`/`those` 在数量前、`have`/`are` 在数量后同理（「these 1 log line」「1 have」）。
2. 「1–${n} chapters」里的数量是范围的终点，永远不是 1，不拦。`pluralEn(...)` 是已按数量变形的名词，不是数量，但它后面的 `have`/`are` 仍随数量变；数量所在分句里带 `and` 的是并列主语，本来就用复数动词。
3. 嵌套的 JSX 表达式与回调体独立访问，不把 `map` 回调的 `desc` 形参单独当作可见文案。

### 三、主进程只有中文的报错（基线）

1. 主进程（`electron/`）里只有中文的报错（#474）按「文件 → 所在函数 → 处数」记在基线里，不记行号：处数超过基线（新增）失败；低于基线（已修）也失败，要求运行 `--update-baseline` 把基线收紧，**基线只减不增**。作者看不到的写 `// i18n-exempt: <理由>`，规则与渲染层相同。

### 四、日文

缺日文不算违规；写了日文却是空字符串才算（运行时会退回英文，等于没写）。运行记录里随运行语言走的两处文案，`ja-JP` 不落库（#725），写日文算违规。
