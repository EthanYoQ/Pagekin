# 打开作品时封存读不出的生成记录

2026-11-18，#702。本 ADR 替换 ADR-0029「后果」第 2 条原来的做法（恢复中断运行时跳过读不出的根）。

## 背景

ADR-0029 承诺一条记录坏了，只有读写它的操作报错。生成账本做不到这一点：

- 账本四张表有六个 JSON 列：`generation_roots.action_json`、`budget_json`，`generation_runs.binding_json`，`generation_attempts.attempt_json`、`usage_receipt_json`，`generation_artifacts.artifact_json`。
- 有近 30 条跨记录的语句，在条件里对这些列用 JSON 函数，或者整列取出再 `JSON.parse`。任何一格读不出，这些语句整条报错。新建生成、全书进行中查询、连续性检查页、选区建议都会因为一条无关的坏记录失败。
- 在读取点上逐个补守卫补了三轮，每轮审计都报出新的读取点，也没有东西拦住以后新写的读取点。
- 应用自己写不出读不出的 JSON，SQLite 的提交是原子的。这种格子只可能来自外部工具改库、躲过 `integrity_check` 的磁盘损坏或手工改过的存档。没有一例用户数据。

## 决定

1. **打开作品、拿到可写句柄之后，对六列做一次进门检查**（`admitGenerationLedger`，在 `initProjectDatabase` 里紧跟 `fenceProjectSession`）。
   - 读得出指四条同时成立：存成 TEXT，不含 NUL 字符，`json_valid` 为真，顶层是对象。`usage_receipt_json` 允许 NULL。
   - 查 TEXT 是因为 BLOB 里的合法 JSON 过不了导出投影。查 NUL 是因为合法对象后面跟 NUL 和别的字节时，`json_valid` 只看 NUL 之前，`JSON.parse` 看全部。查顶层类型是因为 `null` 过得了 `json_valid`，建负责方时却抛错。NUL 按字符查，不按字节：UTF-16 编码的库里健康文本转成字节也带零。
2. **读不出的格子就地换成中性值，同一个事务里做三件事。**
   - 中性值是契约类型的合法取值，并且不会被任何跨记录查询的条件选中：项目号为空串，尝试状态是「结果不明」，预算四项都是 1。
   - 所属的根写 `blocked_code = GENERATION_LEDGER_UNREADABLE`。已有阻断码的根不覆盖。现有代码处处认这一列：拒绝派发、拒绝续跑、不能当父根、批量不可续、视图标为不可重放。
   - 原始字节按十六进制记进所属运行 `binding_json` 的记账区，键是 `$ledgerUnreadable`。根上的格子记在这条根按 rowid 的第一条运行上。`$` 开头的键是运行上的记账区，不属于冻结绑定，冻结绑定读写时自动分开，导出时整份 `binding_json` 被中性化。记账区原来的 `$ledgerUnreadable` 不是数组时，原值按 JSON 文本存成第一条（`{"previous": "原值的文本"}`），再追加，不加深嵌套。
   - 只换坏的那一格。同一棵树里读得出的格子不变，已保存效果的证明都在它们里面。
3. **作品没有坏格子时，检查只是一条只读查询，不开事务、不写库。** 封存之后再扫是空的，所以重复打开没有写入，不需要「已处理」标记。 扫到坏格子时，拿到写锁后再扫一遍，只换仍然读不出的格子：两次扫描之间别的连接可能已经修好了它。
4. **绑定被封存的根按作者可能已保存处理。** 作者保存大纲的回执记在绑定的记账区里，绑定读不出时回执也读不出。这条根拒绝写大纲（`GENERATION_LEDGER_UNREADABLE`）。恢复中断运行照常把它暂停，只改状态，不碰作者的内容；跳过它会让卡住的尝试一直算「进行中」，挡住全书的大纲保存。
5. **封存记录本身就是标记。** `$ledgerUnreadable` 只会出现在被阻断的根的运行上，查它只读这些根的绑定，平时一条也没有。三处用它：
   - 有任何记录被封存过，恢复列表标「部分读不出」，它原来属于哪一项可能已读不出。
   - 一批的根上有封存记录时，这一批不给进度：已提交的章可能认不出，按进度会把写过的章再写一遍。
   - 定稿和导入按槽位找前一次运行，槽位键随绑定一起没了。被封存的运行仍按 `open_key` 里的点击号占住槽位：定稿槽位报 `GENERATION_LEDGER_UNREADABLE`，不另开新根，免得二次提交角色卡或要点。导入的槽位键是哈希，认不出属于哪次导入，而同一次导入的各阶段还互相检查前一阶段的效果，所以有一条被封存的导入运行就拒绝全部导入生成。点击号也读不出时按占用处理。同一槽位里任何一条运行的点击号读不出，报槽位冲突。
6. **进门之后的代码照常信任账本。** 生产路径拿可写句柄只有 `getProjectDb()` 一个出口，它只发出进过门的句柄。各读取点上的 `json_valid` 守卫、跳过读不出的根、计数读不出的收据都删掉。
7. **清单只有一份**（`ADMITTED_LEDGER_CELLS`）。扫描语句从它推导。守卫测试扫源码：跨记录语句在条件或取值列表里解析的账本 JSON 列必须在清单里，以后新写的读取点不在清单里会被拦下。按主键取一条记录（条件里没有 OR）的语句不算跨记录。`open_key` 不进清单：它是唯一身份键，换成中性值会让同一次点击的重试找不到原来的运行。两处按槽位查重试链的语句原样取出 `open_key`，在代码里解析，读不出时按重试链不符报设计码。

## 不采用的做法

- **给 JSON 列加 `CHECK(json_valid(...))`。** 约束被违反时 `integrity_check` 报错，打开校验会把整本书判为损坏。一格的问题变成整本书打不开。
- **隔离表、生成列、索引。** 都会改变结构指纹，要升库版本。迁移通道也不允许在迁移里改已有行的内容，所以改写只能放在打开之后。
- **放在负责方创建时检查。** 负责方之外还有十处直接构造生成运行仓库，导出、删章、重开章节也直接读账本，放在负责方里会漏掉它们。
- **查到就拒绝打开，或停用整本书的 AI。** 比逐点守卫还差，而且作者没有出口。

## 后果

- 书照常打开，其余功能照常。坏的那次生成不能继续、不能重试、不能当续写的起点。
- 三处表现与之前不同，维护者已接受：
  - 坏的是某次批量写作的提交收据时，这一批不再出现在恢复列表里，列表仍标「部分读不出」。
  - 坏的是运行绑定时，那次生成没保存的候选稿从界面上消失，恢复列表标「部分读不出」。原始字节在库里。
  - 坏根没被审修循环引用时，便携存档能导出。之前报 `PORTABLE_UNSAFE_PROJECTION`。
- 绑定被封存的定稿运行挡住同一章同一步的后处理，作者不能对这一步换模型重跑；被封存的导入运行挡住这本书后面所有的导入生成。之前坏绑定让这两条查询整条报错，效果相同。
- 坏根被审修循环引用时，那条循环读写报错，升库版本和导出仍被全书 M03 挡住。这是 ADR-0029 下任何坏循环都有的后果，迁移通道另行收口。
- 只有根、没有运行的根无处记原始字节，照常封存，原始字节不保留。应用建根时总在同一事务里建运行，这种行只可能来自外部改库。
- 打开作品多一次全量 JSON 解析。112 章手动夹具（每章一个审稿类运行）上扫描约 0.2 s，几乎全部花在 `binding_json`，不扫它约 15 ms。代价随绑定字节数增长。
- 回退到 1.4.0 仍能打开：中性值是合法取值，`$ledgerUnreadable` 留在绑定的记账区里，只影响已经封存的那一条运行。
- 不在边界上检查对象内部的字段，比如绑定里某个字段是不是数组。这类错误只有人手改库造得出。

## 后续

- **S2 运行索引**把跨记录解析 `binding_json` 的语句收进索引后，把这一列移出清单，打开时的扫描回到十几毫秒。守卫测试是验收判据。
- **打开后提示一次**：这次打开新封存了记录时告诉作者正文没有受影响。另一个 PR 做。
