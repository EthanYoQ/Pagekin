# 执行层按同一个窗口走，学到的窗口下次直接用

2026-11-10，#279。本 ADR 修订 ADR-0023 决定 2，解决 ADR-0026 决定 3 和 ADR-0027「未决」里留下的问题，不改它们的原文。

## 背景

维护者要求降低报错和让作者调整的操作。现状有三处不一致：

- 租约证据是预设压过手填，额度和设置页是手填压过预设。作者在设置里手填的窗口，写稿时不生效。
- 服务商报过一次超长，软件读到真实窗口，但只记在这次运行里。下一次写稿、批量写稿的下一章还要再撞一次。
- 输出上限大于窗口时，高级设置里常驻一条提示，要作者自己调。

ADR-0026 决定 3 没有动租约证据，因为它进收据、恢复时深比较，改了会让在途运行报「模型变了」。

## 决定

1. **优先级只有一处，加入「学到」：手填 > 学到 > 拉取 > 预设 > 默认。** `resolveContextWindow` 返回窗口和来源，租约证据、可选材料额度、设置页都读它。
2. **学到的窗口存在模型档案的独立字段 `learnedContextWindow`。**
   - 字段里带着学到时的服务商、协议、地址和模型名，身份对不上就不算数，不靠每个修改点去清。
   - 不进 `modelRevision`。
   - 只由主进程写。设置页拿旧数据保存时以盘上的为准，渲染端传来的值不算数。
   - 手填过不用它。来源是拉取、预设时只收紧不放大。来源是默认时服务商报什么都接受，默认值只是猜测。
3. **窗口来源可信时，输出上限收紧到窗口的一半以内。** 可信指手填、学到、拉取、预设。来源是默认时不收紧，默认值可能偏小，按猜测收紧会把正文截短，真超长时走 #649 的学习和重试。这修订 ADR-0023 决定 2 里「上下文窗口不收窄输出」一句；输入估计和根账剩余额度仍不收窄输出。
4. **留一半是因为只收紧到窗口没有用。** OpenAI 兼容服务商把输入和 `max_tokens` 合计算进窗口，硅基流动在 `max_tokens` 本身超过窗口时也拒绝。输出等于窗口时，任何提示词都放不下，可选材料额度也是 0。半数不读输入估计，结果可以冻结进收据。
5. **已开始的运行按开始时的值走。** 收紧后的输出上限在租约证据里，发送时取收据里的值，不按当前档案重算。
   - `modelRevision` 相同时，恢复比较沿用收据里的窗口和输出上限（`withFrozenWindowEvidence`）。学到窗口和本次取值规则变化都不算模型变了。
   - 功能证据（思考、结构化输出、用量）仍要逐项相等。
   - 根预算不变，批量的根早已冻结，之后每章开新运行时读当时的窗口。

## 删除

设置页的「最大输出没有给提示词留下空间」提示。软件已经自动收紧，不需要作者调整。

## 兼容

- 旧收据的 `maxOutputTokens` 按旧规则算过，恢复时按它发送。证据的结构没变。便携导出的字段策略（`portable-project-field-policy.json`）里没有 `capabilityEvidence`，不校验证据内容。
- 证据的 `source` 枚举没有扩充：手填、学到、拉取都记 `user-operational-cap`。`materialDecision.budget.contextWindowSource` 多了 `learned`。

## 后果

- 手填的窗口比服务商实际的小时，输出上限也跟着被压低，属于作者的设置生效。
- 半数是工程取值，没有逐模型实测。窗口很小的本机模型（4,096）输出上限会到 2,048，可能多触发续写。
- 提示词本身超过半个窗口时，服务商仍可能报超长，按 ADR-0023 处理。这里不读输入估计，不做逐请求贴合。
- 设置页的「当前有效输出额度」没有计入这一步收紧。它写的是「最多发这么多」，仍然成立。
- 学到的窗口只收紧。服务商后来放宽限制时，作者手填窗口或换模型身份才会用上更大的值。这是「不增加操作」的代价。
