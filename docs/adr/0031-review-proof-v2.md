# 审修证明只冻结保存要读的字段

2026-11-20，#702 PR 2。

## 背景

审稿、修稿开跑时，主进程把这次要用的全部材料冻结进运行的 `binding_json.sourceManifest`（审修证明）：项目配置、世界观、角色状态、前文全部定稿原文、蓝图、本章目标、预检命中，同一份 JSON 还原样存进作者输入 `review-revision-context`。

前文越长，证明越大，长篇撞上两道上限：

- 作者输入单项 8 MiB（`GENERATION_AUTHOR_INPUT_TOO_LARGE`）：前文 1000 章、每章 3000 汉字时开跑即失败。
- 材料裁决最多 1024 条来源（`MATERIAL_DECISION_MAX_SOURCES`，`GENERATION_MATERIAL_DECISION_INVALID`）：前文 1100 章时开跑即失败。

## 决定

1. **新写入的证明是 v2，只留保存与续跑要读的字段。**
   - 字段：`version: 2`、`operation`、`source`、`sourceHash`、`writingLanguage`、`uiLocale`、`authorInputs`、`frozenGoals`、`preflightFindings`、`wordsPerChapter`、`confirmation?`、`recheck?`、`inputHash`。
   - `inputHash` 是主进程捕获的整份材料（原 v1 去掉 `version` 的全部字段）的 SHA-256。前文原文、配置、蓝图等不再进证明。
   - 体积不随前文章数增长，只随本章正文、确认清单和预检命中条数增长。
2. **材料每次用时都从数据库重新捕获，再按证明的版本冻结一遍比对。**
   - 捕获返回 `{ frozen, materials }`。渲染端拼提示词读 `materials`，作者输入里放 `frozen`。
   - 开跑准入、绑定构建（含重开作品后的重建）和续跑都重新捕获，`freeze(重新捕获, 证明版本)` 与证明逐字段相等才继续，否则报 `GENERATION_REVIEW_CONTEXT_CHANGED`。v1 与改造前完全一样，v2 由 `inputHash` 覆盖不在证明里的材料。
   - 续跑时主进程把重新捕获的材料随恢复信息交给渲染端；已保存的运行只打开收据，不给材料。
3. **v1 继续读、继续写。** 升级前开跑的 v1 运行升级后续跑仍按 v1 重建，不改写成 v2。`readReviewProof`、M03 证明、主进程 `context()`、导出白名单认 v1 和 v2。导出白名单按版本分表：v1 才有的字段出现在 v2 里同样拒绝。
4. **库版本升到 12，不改表。** 版本号只为让 11 及更早的书童拒开含 v2 证明的书：旧版只认 v1，会把 v2 循环当作不可证，整本导不出。便携包的 `PORTABLE_SOURCE_SCHEMA_VERSION` 跟着升到 12，读端仍收 7 到 11；存档 `formatVersion` 不变。M11 的校验与 M10 相同（同一结构指纹）。
5. **去掉 1024 条来源上限。** 审修的每条来源都必须对上主进程捕获的唯一身份，条数受前文章数约束。写稿只取最近 12 章定稿、作者选的候选和参考，不会接近 1024；编辑器选区不走材料裁决。去掉后写稿路径也不再有这道硬上限，靠它自己的选材约束。
6. **脚本读证明也走 `readReviewProof`**（`scripts/review-proof-read.mjs`），守卫测试把解构读取也算作直接读。
7. **导出时封存已保存的 v1 证明（#702 PR 3）。** 只改存档里的副本，源库由决定 8 整理。
   - 对象：审修循环下、收据里记了 `reviewRevisionEffect` 的运行，证明是 v1 全文且自洽。没保存的运行、验不过的证明照原样处理。
   - 封存形是 v2 的字段加 `rewrittenFrom: 1`。`inputHash` 取原 v1 上下文的哈希，也就是收据里的 `contextHash`，收据不改写。清单里的 `reviewRevisionContextHash` 和作者输入副本按封存后的 JSON 重写。
   - `readReviewProof` 给它单独一态 `sealed`。M03、导出和主进程读已保存收据都认它：封存形自身的哈希照常重算，原哈希只和收据比。来源稿、确认稿、复核、审稿正文的核对与 v1 相同。
   - 少掉的是「当时审稿看到的前文和设定的逐字副本」，存档里不能再重算老证明的原哈希。恢复后老章节原来的审修循环本就不可重放（ADR-0018 C17），封存没有拿走能做的事。
   - 存档 `formatVersion`、库版本都不变：已发布的读端最高只收库版本 10 的存档，读到 12 就拒绝。
8. **打开作品时就地封存源库里的同一批证明（#702 PR 4）。**
   - 时机：打开作品的 worker 校验完、主进程拿句柄之前。这时没有别人持着这本书，改写和 VACUUM 不和主进程抢锁。导出时主进程持着可写句柄，不在导出里做。不进迁移：迁移失败会挡住打开，整理失败只记一条警告，照常打开。
   - 对象与决定 7 相同，另要求收据里的 `contextHash` 等于证明重算的哈希：源库没有导出前的从严 M03 兜底。64 KB 以下的不动，导出时照样封存。只换清单里的证明三项，模型收据、来源、`$` 记账原样。
   - 一个事务封存完；空闲页过半才 VACUUM，看的是库的现状，封存提交后、缩文件前被打断，下次打开照样缩。整理改过库就按新字节重算内容身份。
   - 源库里进行到一半的 v1 审修循环在封存的父运行上接着走：续跑读的确认稿、修订稿、收据都还在。

## 后果

- 证明体积（112 章夹具截取前文，待审章 3000 字，无预检命中）：

  | 前文章数 | v1 字节 | v2 字节 |
  |---|---|---|
  | 3 | 42,964 | 9,454 |
  | 48 | 524,543 | 9,457 |
  | 112 | 1,208,331 | 9,460 |

  v2 只随本章正文、确认清单和预检命中条数增长。前文 1100 章短正文、1000 章每章 3000 汉字都能开跑、裁决、保存。
- 改动任一前文定稿、配置或蓝图后续跑，和 v1 一样报 `GENERATION_REVIEW_CONTEXT_CHANGED`。区别是 v1 能从证明里看到当时的全文，v2 只能看到哈希。
- 每次准入、构建和续跑都重新读一遍前文。改造前 v1 也是这样重新捕获后比对，读库次数不变。
- 每位作者升级到这一版后第一次打开大书要付一次升级。1.5.0 的书是库版本 10，走 10→12。112 章夹具的升级耗时见 PR 描述。
- 老书的存档不再带前文副本，存档大小不随章数平方增长。112 章手写夹具的存档库从 145.9 MB 降到 10.8 MB，导出耗时见 #702 PR 3 的描述。
- 打开时整理后，112 章手写夹具（升到 12 后）的源库从 177.6 MB 降到 46.6 MB。第一次打开在 worker 里多花约 1.8 秒，之后每次打开的校验从约 0.9 秒降到约 0.3 秒，导出清洗从约 4.6 秒降到约 1.1 秒。副作用：任何一本书，打开时空闲页过半都会顺带 VACUUM，不只是有旧证明的书。
